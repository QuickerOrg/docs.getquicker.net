# 运行平台、系统要求与 64 位迁移

Quicker 1.x 主程序基于 .NET Framework 4.7.2。Quicker V2 主程序升级为 .NET 10 for Windows，并将正式发布平台统一为 x64。

这是 V2 最底层的一项变化。它同时提高了 Windows 系统版本和位数要求。普通动作通常可以直接迁移，但旧系统，以及依赖旧运行时或 32 位组件的高级用法，需要先处理兼容问题。

## 为什么升级到 .NET 10

.NET Framework 已进入以兼容和安全维护为主的阶段。升级到现代 .NET 后，Quicker 可以继续使用新的运行时、编译器、依赖注入、序列化和性能工具。

这次升级也为新版动作模型、QkEval 表达式引擎、结构化调试、新同步体系和后续功能提供了统一基础。

对普通用户而言，升级主要表现为程序基础设施更新。它不意味着已有动作必须重新创建，但旧脚本和组件不再天然享有 .NET Framework 的全部兼容行为。

## Windows 系统版本要求

Quicker V2 只能在 **.NET 10 官方支持的 Windows 系统**上运行。Windows 7、Windows 8 和 Windows 8.1 不在支持范围内，不能通过补装 .NET Framework 或兼容补丁继续运行 V2。

.NET 10 对 Windows 的支持会跟随 Windows 自身的生命周期调整。不能只看到“Windows 10”就认为一定受支持；当前只支持官方列表中仍处于支持期的 Windows 10 企业版、IoT 或 LTSC 分支。普通用户建议使用仍受支持的 Windows 11 x64 版本。

升级前请查看 Microsoft 维护的 [.NET 10 支持的操作系统列表](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md)。该列表比本文写死一个最低版本号更准确。

> **注意：系统可以启动旧版 Quicker，不代表可以运行 V2**
>
> 1.x 与 V2 使用不同的 .NET 运行平台。安装程序或应用清单中保留的旧 Windows 兼容声明，也不能覆盖 .NET 10 的实际运行要求。

## V2 不再提供 x86 正式版本

Quicker V2 正式安装包只构建和发布 x64 版本。因此：

- 需要使用 64 位 Windows；
- 32 位 Windows 不能安装或运行 V2；
- 不再提供用于 32 位系统的 V2 x86 安装包；
- Quicker 进程内加载的原生 DLL、COM 组件和驱动必须与 x64 进程兼容。

V2 仍可对许多 32 位应用发送按键、鼠标操作或进行窗口控制。受影响的是需要加载到 Quicker 进程内部的 32 位组件，而不是所有 32 位目标程序。

## 哪些动作需要重点检查

### 加载第三方 DLL 的动作

如果 C# 脚本、插件或动作直接加载第三方程序集，应确认该程序集支持现代 .NET 或兼容的 .NET Standard，并且它依赖的原生库提供 x64 版本。

仅面向 .NET Framework、依赖旧配置文件或使用特殊程序集加载方式的 DLL，可能无法直接在 V2 中工作。

### COM、Office 和数据库组件

Excel、Access、OLE DB、ODBC、AutoIt 或其它 COM 自动化依赖可能同时存在 32 位和 64 位版本。

V2 只能在进程内加载与 x64 匹配的组件。如果电脑只安装了 32 位提供程序，相关动作可能出现“未注册类”“找不到提供程序”或 DLL 位数错误。

这不等同于要求所有 Office 软件都必须升级。是否受影响取决于动作采用进程内 COM、外部程序、命令行还是其它通信方式。

### 自定义 C# 代码

现代 .NET 与 .NET Framework 在部分 API 和默认行为上不同。常见风险包括：

- `Thread.Abort` 不再可用；
- `BinaryFormatter` 不再提供可用的内置实现；
- 程序启动、程序集加载和应用域行为发生变化；
- GBK、Big5 等非 Unicode 编码需要明确指定和支持；
- 部分网络、序列化、排序及区域设置行为不同。

V2 已为 Quicker 自身和常见旧动作提供兼容处理，但无法替所有用户代码保证行为完全一致。

## 升级后的建议验证

先确认 Windows 版本位于 .NET 10 官方支持范围内，再安装 V2 并优先验证以下动作：

1. 调用本地 DLL、COM、Office、数据库驱动或硬件 SDK 的动作；
2. 使用 C# 代码、外部程序集或旧 CodeDOM 编译方式的动作；
3. 读写 ANSI、GBK、Big5 或其它旧编码文件的动作；
4. 依赖强制终止线程、应用域隔离或旧序列化格式的动作；
5. 与浏览器扩展、辅助进程或本地服务通信的动作。

建议先复制动作进行测试，保留原动作和输入数据。不要在确认兼容前直接覆盖唯一可用版本。

## 遇到位数问题时怎么办

可以按下面顺序排查：

1. 确认 Windows 版本仍在 .NET 10 官方支持范围内；
2. 确认 Windows 为 64 位系统；
3. 确认错误组件由 Quicker 进程内加载，还是由外部程序单独运行；
4. 为 DLL、COM、ODBC 或 OLE DB 安装 x64 版本；
5. 如果组件只有 x86 版本，考虑改为调用独立的 32 位辅助程序，再通过文件、命令行或进程间通信交换数据；
6. 保留错误信息、动作导出文件和组件版本，便于进一步诊断。

## 界面或远程桌面显示异常

V2 在“设置 → 基础设置”中提供“兼容渲染模式（软件渲染）”。它主要用于窗口内容缺失、显卡驱动兼容或远程桌面环境中的显示问题。

修改后需要重启 Quicker。软件渲染会降低界面绘制性能，不建议在显示正常时长期开启。

如果 Quicker 无法正常显示设置窗口，还可以使用应急文件 `C:\qk_disable_gpu.txt` 强制禁用 GPU。应急文件的优先级高于设置页选项，排障结束后应检查是否仍需保留。

> **说明：项目文件中仍可能保留历史平台配置**
>
> 源码中的部分项目仍保留 x86 条件或兼容构建配置。这不代表 V2 会继续发布 x86 正式安装包；正式发布链固定生成 x64 版本。
